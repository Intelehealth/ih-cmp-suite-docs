TSI DPDP CMS API

Every function is called as POST /api/v1/{category}/{service}/{func} with a JSON body. The function name may instead be sent as _func in the body to /api/v1/{category}/{service}; when both are given, the body's _func is the one that runs.

The body is validated against the function's schema before it runs; a failure is a 400 whose message lists what is wrong.

Tenancy. On the client API, fiduciary_id is taken from the credential. A value sent in the body is overridden, so a key or token can never read or write another fiduciary's records. With a principal token, user_id is taken from the token too; a user_id in the body that does not match it is refused with 403. A function under /api/v1/public/ has no credential and takes fiduciary_id from the body.

GET. A function may be called with GET only when it is a read; parameters then travel in the query string. Query values are strings and are validated like a body, so GET is documented only where every required parameter accepts a string, and only those parameters are listed. Everything else is POST-only (405 otherwise). A credential is never read from the query string.

Errors. Every error has the same body: timestamp, status, error, message, path.

Authentication (client API). Either an application API key (X-API-Key and X-API-Secret headers, together) or a data principal's bearer token. An API key carries scopes (READ, WRITE, PURGE); each function states the scope it needs, and a key without the scope gets 401. PURGE functions do not accept a principal token. Functions under /api/v1/public/ need no credential.
